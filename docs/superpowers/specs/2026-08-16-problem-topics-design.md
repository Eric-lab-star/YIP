# 문제 주제 분류 설계

2026-08-16 · `/problems` 개선 2단계

1단계(PR #46)는 검색과 필터를 넣어 131개 목록을 좁힐 수 있게 했다. 이 문서는
그 다음 — 목록을 **주제별로 묶는 것** — 을 다룬다.

## 문제

`/problems`는 131개를 `createdAt` 순서로 한 줄씩 나열한다. 검색과 필터가
생겼어도 "무슨 주제가 있는지" 를 훑을 방법이 없다. 목록을 처음 여는 사람은
여전히 131행을 마주한다.

## 결정된 것

세 가지를 사용자와 정했다.

**주제는 커리큘럼과 독립이다.** 강의 순서를 그대로 비추는 게 아니라 문제만의
분류 체계를 둔다. 강의가 바뀌어도 주제는 그대로일 수 있고, 강의에 없는 문제도
분류된다.

**한 문제는 주제 하나를 가진다.** 태그가 아니다. 그래야 목록을 겹치지 않는
섹션으로 접을 수 있고, 그게 원래 요구였던 "훑어보기" 에 직결된다.

**주제는 DB에서 관리한다.** 코드 상수가 아니라 컬렉션이고, 관리자가 화면에서
추가·이름변경·순서변경한다. 주제를 하나 늘리는 데 배포가 필요 없다.

## 지금 데이터에 무엇이 있나

측정한 사실이다. 설계의 근거이므로 남긴다.

```
DB 의 문제                                        131개
  난이도 medium                                   100개
  난이도 easy                                      31개
  난이도 hard                                       0개

Algorithm 레슨이 /problems/<slug> 로 링크하는 문제  113개
  링크됐는데 시드에 없는 것                           0개   ← 완전히 일치
어느 레슨도 링크하지 않는 문제                       18개
  기초 문제 (seed-simple-problems.mjs)              17개
  two-sum-stdin (초기 시드의 잔재)                    1개
```

23개 Algorithm 챕터가 각각 5문제씩(`list_search`만 3개) 링크한다. 다른 섹션
(AIDeveloper, PublicDataViz, tourOfPython, simpleWebDev, spaceshipCaptain)은
문제를 전혀 링크하지 않는다.

**이 레슨 링크가 백필의 출발점이다.** 그 문제를 가르치는 챕터가 직접 링크하니
현재 존재하는 가장 좋은 신호다. 다만 어디까지나 출발점이고, 백필 이후의 진실
소스는 `topicSlug` 필드다 — 주제는 커리큘럼과 독립이기로 했으므로 이후 둘은
자유롭게 갈라진다.

## 데이터 모델

### 새 컬렉션 `topics`

```ts
export interface Topic {
	_id?: ObjectId;
	/** URL·참조용 식별자. 문제 slug 와 같은 규칙: /^[a-z0-9-]+$/ */
	slug: string;
	/** 화면에 보이는 이름. 자유롭게 바꿀 수 있다. */
	name: string;
	/** 목록에서의 섹션 순서. 작을수록 위. */
	order: number;
	createdAt: Date;
	updatedAt: Date;
}
```

`slug`에 unique 인덱스, `order`에 정렬 인덱스를 건다.

`name`과 `order`는 바뀌는 값이고 `slug`는 문제가 가리키는 키라 **불변**으로
다룬다 (문제의 `slug`가 불변인 것과 같은 이유 —
`app/lib/mongo/problems.ts`의 `updateProblem`이 slug로 매칭한다).

### `Problem`에 필드 하나

```ts
export interface Problem {
	// ... 기존 그대로
	/** 소속 주제의 slug. 미분류면 없음. */
	topicSlug?: string;
}
```

**참조이지 복제가 아니다.** 주제 이름을 바꾸면 `topics` 문서 하나만 바뀌고
131개 문제는 손대지 않는다. 이름을 각 문제에 복제했다면 이름 변경이 131건
쓰기가 된다.

`topicSlug`를 **선택 필드**로 둔다. 미분류 상태가 정당하게 존재하기 때문이다 —
지금도 `two-sum-stdin`이 그렇고, 관리자가 새 문제를 만들 때 주제를 아직 안
정했을 수 있다.

### 삭제 시 무결성

주제를 지울 때 그것을 가리키는 문제가 하나라도 있으면 **거부한다.** 관리자가
먼저 문제들을 옮겨야 한다.

대안은 문제들을 미분류로 떨어뜨리는 것인데, 실수로 주제를 지웠을 때 5개 문제의
분류가 조용히 사라지고 되돌리려면 하나씩 다시 지정해야 한다. 거부는 시끄럽고
복구할 게 없다.

## 백필

되돌리기 번거로운 유일한 단계라 절차를 명시한다.

`scripts/backfill-problem-topics.mjs`:

1. `app/Algorithm/*/**/*.mdx`를 훑어 `/problems/<slug>` 링크를 모아
   `챕터 → [문제 slug]` 매핑을 만든다
2. `utils/curriculum/Algorithm.ts`의 순서대로 `topics` 문서를 만든다
   (`slug`는 챕터 slug, `name`은 챕터 `name`, `order`는 배열 인덱스)
3. 기초 17문제를 위한 `기초` 주제를 `order: 0`으로 맨 앞에 넣는다
4. 매핑대로 각 문제에 `topicSlug`를 지정한다
5. `two-sum-stdin`은 **미분류로 남긴다** — "두 수의 합" 제목이 3개 중복인
   것의 하나이고, 어느 주제에 속하는지는 콘텐츠 판단이라 스크립트가 정할 일이
   아니다

**성질**: 다시 실행해도 안전해야 한다(slug로 upsert). `--print`로 무엇을
바꿀지 먼저 보여주고, 실제 쓰기는 별도 플래그로만 한다. 저장소의 다른 시드
스크립트가 이미 이 관례를 따르므로 `scripts/lib/mongoUri.mjs`를 그대로 쓴다.

**초기 주제 이름이 커리큘럼에서 온다고 해서 커리큘럼에 묶이는 건 아니다.**
시작점일 뿐이고, 그 뒤로는 관리자가 자유롭게 이름을 바꾸고 순서를 옮기고 새
주제를 만든다.

## 화면

### 목록 — 접힌 섹션

지금 목록의 문제는 131행이라는 것이다. 주제로 묶기만 하고 전부 펼쳐두면 그대로
131행에 소제목만 24개 늘어난 셈이라 아무것도 해결되지 않는다.

**섹션은 기본으로 접혀 있다.** 처음 열면 24줄짜리 목차가 보인다:

```
▸ 기초                        17문제 · 17 완료
▸ 리스트와 탐색                 3문제 ·  0 완료
▸ 문자열 기초                   5문제 ·  0 완료
...
▸ 미분류                        1문제 ·  0 완료
```

한 줄에 주제 이름, 문제 수, 완료 수. 펼치면 지금과 같은 행들이 나온다.
미분류는 항상 맨 뒤.

### 1단계 검색·필터와의 관계

검색어나 필터가 걸리면 **일치하는 문제가 있는 섹션만 남기고 자동으로
펼친다.** 접힌 채로 두면 "131개 중 3개" 라고 해놓고 화면에 아무 문제도 안
보이는 상태가 된다.

빈 섹션은 숨긴다. 개수 줄("131개 중 3개")은 지금처럼 전체 기준으로 유지한다.

접힘 상태는 화면 안 상태로만 둔다. URL에도 저장소에도 넣지 않는다 — 1단계에서
필터 상태를 URL에 안 넣기로 한 것과 같은 이유로, 프리렌더된 페이지에 라우터
갱신을 얹을 값이 아직 없다.

### 관리자 — 주제 관리

`/problems/topics` (관리자 전용). 목록 페이지의 `새 문제` 버튼 옆에 진입점을
둔다.

**경로 충돌 주의.** `app/problems/topics/`는 정적 세그먼트라 `[slug]`보다
우선한다. 즉 이 라우트를 만드는 순간 **`topics`라는 slug를 가진 문제는 영영
열 수 없게 된다.** `new`가 이미 같은 이유로 예약돼 있다
(`app/problems/new/page.tsx`). 문제 생성 폼의 slug 검증에 예약어 목록
(`new`, `topics`)을 넣어 애초에 만들 수 없게 막는다.

- 주제 목록을 `order` 순으로 보여주고, 각 행에 문제 수
- 추가: `slug` + `name`
- 이름 변경: `name`만
- 순서 변경: 위/아래 버튼 (드래그는 지금 필요 없다)
- 삭제: 문제 수가 0일 때만 활성

**권한 확인은 페이지 본문에서 한다.** `requireAuth()`는 누구인지만 증명하고
무엇을 할 수 있는지는 증명하지 않는다 — `app/dashBoard/page.tsx`가
`student.role !== "admin"`을 본문에서 검사하는 것과 같은 방식이다. 레이아웃이
대신 해주지 않는다.

### 문제 편집 폼

`problemFormSchema`에 `topicSlug: z.string().optional()`을 더하고, 폼에 select를
하나 넣는다. 선택지는 `topics`에서 온다. "주제 없음"이 유효한 선택지다.

## API

`/api/problems`가 각 문제에 `topicSlug`를 실어 보낸다.

주제 목록은 **같은 응답에 함께 보낸다**:

```
{ topics: [{ slug, name, order }], problems: [{ slug, title, difficulty, solved, topicSlug }] }
```

별도 `/api/topics`를 만들지 않는 이유 — 목록 화면은 항상 둘을 같이 필요로 하고,
지금 `useSWR("/api/problems")` 하나로 끝나는 것을 두 개로 늘리면 두 응답이
어긋난 순간(새 주제는 왔는데 문제는 옛날 것) 을 화면이 처리해야 한다.

**이는 응답 형태가 배열에서 객체로 바뀌는 변경이다.** `/api/problems`를 쓰는
곳을 전부 같이 고쳐야 한다. 관리자 화면은 쓰기가 필요하므로 Server Action을
쓴다 (저장소 관례: 모든 DB 쓰기는 `app/actions/`).

## 프리렌더를 유지한다

`/problems`는 `revalidate = 3600`으로 프리렌더된다. `force-dynamic`이던 시절
모든 방문자가 캐시 미스로 TTFB 280ms를 물었고 지금은 55ms다.

**주제 묶기가 이걸 깨면 안 된다.** 주제도 문제와 마찬가지로 모두에게 같으므로
서버에서 함께 렌더하고, 사용자별인 것(완료 표시·완료 수)만 브라우저에서
채운다. 지금 구조 그대로다.

빌드가 Mongo에 못 닿을 때의 폴백(`ClientProblemList`)도 주제를 함께 받아야
한다. 프리뷰 빌드가 실제로 이 경로로 죽은 적이 있다.

## 하지 않는 것

- **태그(다중 주제)** — 한 문제 한 주제로 정했다. 나중에 필요하면 별도 필드다.
- **주제별 진도 페이지** — 목록의 완료 수로 충분한지 먼저 본다.
- **드래그 순서 변경** — 위/아래 버튼으로 시작한다.
- **주제 slug 변경** — 문제가 가리키는 키라 불변으로 둔다. 정말 필요하면
  새 주제를 만들고 문제를 옮긴다.

## 열린 질문

- **"두 수의 합" 제목 3개 중복** (`two-sum-stdin`, `s-sum-two`,
  `s-two-sum-count`). 주제로 묶으면 서로 다른 섹션에 흩어져 덜 눈에 띄겠지만
  사라지지는 않는다. 콘텐츠 판단이라 이 작업에 포함하지 않았다.
- **`list_search` 챕터만 문제가 3개**다. 의도인지 빠진 것인지 확인하지 않았다.
- 백필 후 **`두 수의 합` 계열이 어느 주제로 가는지**는 레슨 링크가 정한다.
  결과를 사람이 한 번 봐야 한다.
